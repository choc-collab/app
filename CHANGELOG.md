# Changelog

All notable user-facing changes to Choc-collab are documented in this file.

The format is loosely based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html) (pre-1.0 — minor bumps may include breaking changes).

## [Unreleased]

### Added
- **A product's nutrition tab now tells you whether it's ready for a label** — the panel already warned when some ingredients had no nutrition data, but not whether the totals actually satisfy what your market requires on a printed label; those are different questions and only the second one blocks printing something compliant. It now says either "All nutrients required for an EU label are present" or names exactly what's missing and where to add it. The ingredient pages have carried the same check for a while; this brings the product roll-up in line, which matters now that Shop boxes print nutrition labels.

### Changed
- **Every pantry detail page is now directly editable — the pencil, the Save button and the "unsaved changes" warning are gone** — nine pages (Fillings, Ingredients, Products, Packaging, Collections, Moulds, Decoration materials, Shell designs and Product categories) hid their fields behind an Edit pencil, made you fill in a form, and then asked you to Save. Now you click a value and change it, and it's stored. Fields commit as you'd expect: dropdowns and toggles the moment you pick, text and numbers when you leave the field, notes a moment after you stop typing (and immediately if you click away). Nothing is lost by navigating away mid-edit, so no page interrupts you with a browser dialog any more.
  - **A two-column layout separates what you change from what the app works out** — the left column holds what you edit; a sidebar on the right holds what the app tells you: computed **Derived** figures, stock status, and the **Used in** list of everything that references the record. Below `lg` it stacks into one column. The Products *Cost*, *Nutrition*, *Filling history* and *Batches* tabs, and the Collections *Pricing & margins* tab, run full-width instead — their tables and charts don't fit beside a 320 px column.
  - **A record that doesn't exist now says so** — visiting a deleted or mistyped record used to sit on "Loading…" forever. Pages now show a shaped loading skeleton while reading, and a distinct "This ingredient doesn't exist. It may have been deleted." with a way back when it genuinely isn't there.
  - **A save that fails now tells you** — without a Save button there's nothing to turn red, so a failed write raises a toast naming the field ("Notes wasn't saved.") with a **Retry** that replays just that one field. Successful saves are deliberately silent: the value in front of you is the confirmation.
- **Fillings detail page rebuilt around the recipe** — the ingredient list, method and notes sit in the main column with the recipe tab strip; category, status, shelf life and measured yield moved to the sidebar alongside allergens, recipe weight and a new **cost per kg**. Creating a new version is now a promoted action in the header rather than buried below the fold. The confirmed-filling lock now guards only the recipe, so you can still correct a note or a shelf life on a confirmed filling without unlocking it.
- **Filling stock and batch history on the filling itself** — a sidebar **Stock** card shows what's available, what's in the freezer, and when you last made it; a **Batches** tab lists every batch ever recorded, newest first, with what's left of it, a frozen badge, and a link to the plan that made it. The tab only appears once there's stock to show.
- **Packaging purchases are a proper table** — date, supplier, quantity, total and per-unit across sortable columns with a running total in the header, and a permanently visible add row at the bottom instead of a disclosure. Removing an entry replaces the row in place with a confirmation naming the order ("Remove the 4 Nov order — 250 units, €310.00?"). The sidebar reports latest and average per-unit cost, units ordered, orders logged, and when you last ordered.
- **Product fill percentages stay coherent** — editing one filling's share now rebalances the others in proportion and writes the whole split at once, so the parts always add up to 100%. Previously each row was written on its own and a split could quietly drift off 100.
- **Ingredient composition percentages no longer block saving** — the composition figures had to total exactly 100% before the form would save, which made it impossible to record what you actually know from a spec sheet and leave the remainder unaccounted. The card now reports "94.5% accounted for" as information and saves regardless.
- **Ingredient pricing saves as a group** — quantity, unit, grams-per-unit and price commit together when you leave the card, not one at a time. Editing them individually would have banked a price that never existed (changing "10 kg for €50" to "5 kg for €25" one field at a time momentarily reads as €0.010/g), polluting the price chart and every affected product's cost history with a phantom spike.
- **Product categories: the shell-percentage rule is enforced where it happens** — the default shell % must sit inside the min–max range, and typing one outside it now shows the reason against the field ("Must sit between 10 and 20. Not saved — the stored value is still 30%") while keeping what you typed so you can correct it. Min and max still save freely, because moving a range upwards has no valid order otherwise; if that leaves the saved default stranded outside the new range, the card says so until you fix it.
- **Product shell and fill configuration keeps a Save button** — the one deliberate exception. Category, default mould, shell chocolate and shell % are read together by the production planner and the cost engine, and some invalid combinations have no way out one field at a time, so that group commits as a unit with its errors shown inline.

### Fixed
- **The Collections "not found" state was unreachable** — a missing collection fell through to a permanent "Loading..." because the page tested for a value the data layer never returns.
- **Allergen, price-history and cost-snapshot updates survive the switch to per-field saving** — changing an ingredient's allergens still cascades to every filling that uses it (including through nested fillings), a price change still records a history entry and refreshes the cost of every product built on it, and changing a product's mould or shell still writes a cost snapshot.
- **"Used in" no longer prints its heading twice** — the sidebar card's title and the panel's own "Used in 3 products" line were both rendering. The card now carries the title and the count, and the panel just lists.
- **The filling detail page's back link says "Fillings"** instead of a bare "Back", matching every other detail page.
- **A one-product box no longer reads "1 products × €0.57"** in the collection cost breakdown.
- **Product fill percentages of a single filling can no longer be set below 100%** — a sole filling occupies the whole cavity by definition, so typing a lower number left the rest of the fill unaccounted for.

## [0.7.0] — 2026-09-08

### Added
- **Orders & Events — capture future demand months ahead, refine it as the date approaches** — a new top-level Orders area (calendar icon in the nav, sage accent) for corporate orders, market stalls, restaurant orders, and private commissions. An order starts as vaguely as a title and a date ("Popup in Wittelte — Dec 20") and firms up over time: lifecycle statuses (Lead → Confirmed → In production → Fulfilled, plus Cancelled) advance with one-tap pills on the detail page, and a source tag (Market / Holiday / Restaurant / Private person / Other) keeps the calendar scannable.
  - **List view** — upcoming open orders grouped by month, with each card showing the status badge, customer, venue, and how far out the event is ("in 3 months"). Past and closed orders are hidden by default.
  - **Filter panel** — the same funnel-icon panel as the other list pages: show/hide past & closed orders, bound the window to within 30 days / 90 days / 12 months, and narrow to a single customer via a dropdown. Search covers title, customer, and venue.
  - **Month calendar view** — a proper month grid (toggle at the top right, same control style as the product list's Default/Compact switch). Orders appear as chips on their day with a status dot; clicking an empty day opens the quick-add prefilled with that date.
  - **Line items** — itemise what an order needs, as vaguely or precisely as you know it: "40 × (mix TBD, nut-free option)" works fine, and later becomes "40 × Milk Chocolate Ganache". Once a line has a real product, a fulfillment chip tracks how much of it is covered by batch allocations.
  - **Linked batches with per-product allocations** — tie an order to the production batches that fulfil it. A link starts as a loose "this batch is for this order" association and refines into per-product claims: "20 × Salted Caramel from batch 20260902-001", shown against the batch's output ("of ~112") with a soft warning when you over-allocate. A batch that makes hundreds of pieces across several products can serve several orders at once.
  - **Today dashboard tile** — "Upcoming orders" joins the dashboard, listing the next few open orders with status badges and dates.
- **Customers** — a second tab on the Orders page holds the people and businesses behind the orders: name, email, phone, a multi-line address, Instagram handle, and free-form notes. Each customer's detail page shows their **full order history** (upcoming and past). Orders reference customers via a picker with an inline "+ New customer…" quick-create. Deleting follows the familiar pattern: customers with orders are archived (hidden from pickers, preserved on existing orders) rather than deleted; unused ones can be removed after a confirmation.
- **Demo data** now seeds two customers and three orders (a market lead, a confirmed corporate order with line items and a batch allocation, and a fulfilled wedding) so the Orders area and the new dashboard tile are populated on first load.

### Changed
- **Batch summary (recall snapshot) lists each filling's recipe inline** — the plain-text summary written when a batch is marked done now breaks down every filling's scaled ingredients and nested-filling components under its header ("500g caramel base + 5g peppermint oil"), while leaf ingredients still aggregate globally in the "Ingredients used" section for recall traceability.
- The Today dashboard tile row accommodates five tiles on wide screens.

### Fixed
- **Backups now include Orders data** — the orders, customers, line-items, and batch-link tables are exported, imported, and cleared alongside everything else. (Only relevant within this release cycle — earlier versions had no Orders tables.)
- **Deleting a production plan no longer strands its standalone-filling rows** — fillings-only and hybrid plans left orphaned `planFillings` rows behind on delete; the cleanup transaction now covers them (and the new order↔batch links).
- **Best-by date corrections on production batches** (#57).
- Hosting redirect fixes for the app's static-export routing on Cloudflare Pages and Vercel.
## [0.6.2] — 2026-08-28

### Fixed
- **Moulds silently dropped into a generic "Chocolate" group instead of Dark/Milk/White** — the production Shell/Cap tabs, the Products list (coating filter chips, card subtitle, detail-page label), and the cost-breakdown chart's shell-segment colour all grouped/coloured products by the deprecated `Product.coating` free-text field. Products set up via the current shell-ingredient picker never write that field, so they always fell into an "uncategorised" bucket — even when their shell ingredient was properly mapped to Dark/Milk/White under Ingredients → Shell chocolate. All five spots now resolve the coating type from the shell ingredient's mapping first, falling back to the legacy field only for older records that predate it. This also fixes the seed-tempering weight panel on the Shell tab, which used the same broken lookup to decide whether to show itself and which batches to total.

## [0.6.1] — 2026-07-14

### Fixed
- **Filling & shell weights were overstated (a density bug), throwing off costs and nutrition** — the fill calculation multiplied filling by a ganache-density factor (1.2) but never applied it to the shell, so a filled bonbon's parts no longer added up to the mould's cavity weight (e.g. a 13 g mould showed 9 g filling + 5.5 g shell = 14.5 g, and the shell % was skewed). `cavityWeightG` is the manufacturer's stated mass of a fully filled cavity, so filling + shell now reconcile to it directly with no density conversion — the same 13 g mould correctly shows 9 g filling + 4 g shell. **Products entered by grams keep the exact grams you typed** (a one-time data migration preserves them); percentage-mode products' computed filling drops ~17% to a physically consistent value. Cost and nutrition figures update accordingly.

### Changed
- **One-tap cost recalculation after the weight fix** — because stored cost snapshots hold the old gram figures, the What's New banner for this release offers a "Recalculate all costs now" button that writes a fresh, corrected cost snapshot for every product. Each product's cost history labels the update as a *bug-fix correction* so the change is traceable, and prior snapshots are preserved as history.

Read-only summary view with an Edit button that opens the same draft/save/cancel flow as the Target Market tab; navigating away with unsaved changes prompts a confirm. The label editor's `logo`, `company`, `contact`, `socials`, and `qr` fields all pull from this profile — fill it in once and every template you design from then on is already populated.
  - **Settings → Printing** — one default-template slot per kind (Production batches, Filling batches, Boxes) so the picker pre-selects your go-to design for each entry point. Empty value keeps the picker neutral for users who'd rather choose per-batch. The previous Niimbot-specific localStorage toggle and its UI are removed.

Auto-saves on every gesture-end and inspector edit; a tablet/phone warning banner appears when the viewport is coarse-pointer + narrow because drag-to-position is awkward on touch.

The kind is chosen on the new-template page and stays fixed; it determines which print entry points can pick the template (production page only offers production/filling-batch templates, shop only offers box templates, stock-page tabs filter similarly) and what the editor preview's "Preview against" dropdown enumerates. Legacy templates created before this field default to production-batch on read so existing setups keep working without manual migration.

PNG (default) rasterises each label as a high-DPI image; one PNG per context, share-sheet on touch devices and direct download on desktops. PDF generates one multi-page document for the whole print run (one page per label) via `svg2pdf.js` → `jsPDF`, vector throughout so it scales without pixelation. PDF deps are lazy-loaded — PNG users don't pay the bundle cost. svg2pdf's incomplete `dominant-baseline="hanging"` handling is patched in the PDF path so text doesn't clip at the top edge.
  - **18 field types** — Product / batch (auto-bound from the previewed source): name, subtitle, net weight, ingredients, allergens, nutrition table, best-before, batch number, production date, origin / cocoa %. Brand / business (auto-bound from the Brand profile): logo, company info, contact, links, QR code. Custom (manual content): free text, divider line, image upload. Per-field inspector controls for size (pt stepper with a default-reset chip), bold / italic toggles, a curated cross-platform font picker (Helvetica, Arial, Verdana, Trebuchet, Georgia, Times, Palatino, Courier, Menlo, Impact — eleven options grouped by sans / serif / mono / display), a free-form date format pattern (any text with `YYYY / YY / MM / M / DD / D` tokens, plus six one-click presets — ISO, EU, US, DE, NL, short — so adding a regional date layout never needs a code change), allergen emphasis on the ingredient list, QR URL override, and image upload for the image field.
  - **Multi-select, alignment, distribute** — Shift-click to add fields to the selection. When 2+ are selected, a floating toolbar appears above the canvas and the inspector swaps to alignment controls: six align actions (left / centre-horizontal / right / top / middle / bottom) anchored to the selection's bounding box, plus distribute-horizontally / distribute-vertically (anchors the outermost fields and equally spaces the gaps between every field in between; no-op below 3 selected).
  - **Editor polish — keyboard, clipboard, history** — `⌘Z` / `⌘⇧Z` (and `⌘Y`) step undo / redo across every edit (50-entry history). `⌘C` / `⌘V` copy and paste fields via an in-editor clipboard (separate from the OS clipboard so paste is deterministic). `⌘D` duplicates the selection in place with a small offset. Arrow keys nudge selected fields by 1 mm (5 mm with Shift). `Delete` / `Backspace` removes them. All shortcuts skip when the user is typing in an input / textarea / contentEditable so the browser's native text-editing shortcuts still work. Image uploads larger than 1500 px on their longest edge are auto-downscaled through an offscreen canvas before being stored — keeps a 12-megapixel phone photo from bloating the template row and Dexie Cloud sync payload.

  - **Social icons** — the `socials` field swaps the text label for a small SVG icon when the label matches a known network (Instagram, Facebook, X, Twitter, TikTok, YouTube, LinkedIn, WhatsApp, Email, Phone, Website). Future i18n work (German and Dutch are the planned next pair) will route these prefixes through a `marketRegion`-driven locale lookup so the same template prints correctly in every language without per-template edits.

Aggregated allergens, facility "may contain" advisories from `userPreferences.facilityMayContain`, and per-100g nutrition flow through the same `LabelContext` shape regardless of source.

Shop's Ready to sell tab adds a 🖨 Label button next to + Note / Sell on every prepared sale row (and grouped row), printing for that exact box's per-cavity composition. Stock page adds a 🖨 Label button on every product-stock and filling-stock row for one-off relabelling (filling-stock rows added manually outside a production plan hide the button — there's no source plan to build context from). Each click opens the template picker filtered to the right kind (pre-selected to your kind-specific Settings default), renders the chosen template against the resolved context(s), and hands the resulting PNGs or PDF to `navigator.share` on iOS / iPadOS / Android Chrome — where AirDrop, Photos, and label-printer-app extensions actually live — or triggers direct downloads on Mac / Windows / Linux / Chromebook desktops where the OS share sheet doesn't offer useful save-to-disk actions.
  - **EU FIC-style behaviour, market-aware** — ingredient lists are sorted descending by mass per piece, ingredient names render with allergens emphasised bold inside the list (per FIC emphasis rules) with a per-field toggle to disable. The allergen declaration is prefixed with `Contains:` and renders mandatorily bold; the facility advisory line is prefixed with `May contain:` and stays italic + muted by convention. The nutrition table renders as a boxed market-aware panel — outer border, regulatory title at top, right-aligned `per 100g` column header, indented sub-nutrients, and section bars between major nutrient groups (energy / fat / carbs / protein-salt for EU). US/CA get slightly heavier rules in a nod to FDA-panel conventions.
  - **Sensible filenames** — every downloaded file follows `{ContextName}_{Identifier}.{ext}` where the identifier picks the batch number first (so multiple batches of the same product stay distinguishable), then the production / packing date (ISO `YYYY-MM-DD` for archival sorting), then today as the last fallback. Multi-context PDFs that share a batch number are named after the batch (`B2026-05_2026-05-14.pdf`) so a Downloads folder with many runs stays scannable. In-print-run collisions get ` (2)` / ` (3)` suffixes. No more UUIDs, no more `label_` prefix, case and spaces preserved.

Self-contained `<svg viewBox="0 0 widthMm heightMm">` with `<text>` / `<image>` / `<rect>` / `<line>` per field — no `<foreignObject>`, no headless browser. ### Fixed
- **Single-product boxes / bar / snack sales printed empty labels** — the collection-package resolver iterated `collectionProducts` and skipped any product that wasn't in the collection's assortment (a bar product isn't a "bonbon" in `collectionProducts`; a single-product box only references one of N products). The resolver now drives every per-product loop from the sale's actual `cells` distribution and loads any product / mould / filling that cells reference even when they're not collection members.
- **Net weight printed as one piece instead of the whole box** — collection-package and filling-batch resolvers were storing the per-piece average in `perCavityWeightG`, expecting templates to set `piecesPerLabel = N` to scale. That coupled templates to one packaging capacity. Both resolvers now store the *total* weight in that field, and `effectiveLabelWeightG` hard-forces the multiplier to 1 for non-production-batch sources so legacy templates carrying a stale `piecesPerLabel` don't silently corrupt the output.
- **Box best-before always showed "—"** — `Sale.preparedAt` is the packing date, but the resolver never received it. Now threaded through `loadCollectionPackageContext`'s fourth argument; the shop print flow passes it, and `bestBefore = preparedAt + earliest product shelf-life across the actual box contents`.
- **Editor preview for box templates showed empty / wrong data** — the preview source dropdown for collection-package kinds didn't know about real sales, so it fell back to "one of each from `collectionProducts`" — which showed 1 piece instead of 9 for a single-product box, and zero data when the sale's products lived outside the collection assortment. The reactive hook now queries the most recent matching `Sale` for `(collectionId, packagingId)` and threads its cells + `preparedAt` so the preview matches what the user will actually print.
- **PDF labels clipped text at the top edge** — `svg2pdf.js` doesn't reliably honour `dominant-baseline="hanging"`, placing `y` at the text baseline rather than the top of the glyph box; ascenders rendered above the page. The PDF path now pre-processes the SVG, strips the hanging attribute, and shifts `y` down by ~0.8 × font-size so the output matches the on-screen preview.
- **`Pieces / label` row was visible (and dangerous) for every template kind** — for filling-batch and collection-package templates, multiplying the already-total weight by `piecesPerLabel = 9` would print 810 g instead of 90 g. The inspector now only shows the row for production-batch templates.
- **`commercialName` leaked into ingredient lists and shell-origin** — production-batch used `Ingredient.name`, but filling-batch and collection-package used `commercialName ?? name`, producing inconsistent labels for the same ingredient depending on which entry point printed it. All four label fields (production-batch ingredients, filling-batch ingredients, collection-package ingredients, shell origin) now use `Ingredient.name` exclusively. `commercialName` stays editable on the ingredient form for internal use, but never appears on a printed label.
- **Allergen separator** — the allergen declaration line now joins entries with `, ` instead of ` · ` (closer to FIC convention).
- **Ingredient list wrapped with a leading comma** — when a long ingredient list broke across lines, the `", "` separator could be kicked to the start of the next line, rendering as `, Felchlin Sao Palme` rather than keeping the comma after the preceding word. The wrap algorithm now glues a separator that doesn't fit onto the end of the current line (negligible ~1 mm overflow) so commas always trail their word.
- **Filename leakage** — generated PNGs and PDFs no longer contain UUIDs (`label_Salted Caramel_5f3a8c92-d4e2-…png`); see the "Sensible filenames" addition above.

### Changed
- **Settings → Brand → Links picker** — the label/URL freeform inputs are replaced by a curated dropdown (the 10 networks listed in the Brand addition above) plus a "Custom…" escape hatch. Selecting a known network changes the URL input's placeholder to a network-specific hint. Existing free-text entries that don't match the catalog open as Custom rows automatically.

## [0.5.0] — 2026-05-10

### Added

You can give away a packed box, a snack-bar pack, a single bar, or loose pieces, and choose whether they come from stock or off-the-books. A stacked revenue chart breaks the period down by collection (monthly or weekly granularity, toggleable). Four leaderboards rank best-selling bonbons, best-selling bars, best-selling box sizes, and collections by revenue — each with a *↑ Rising / ↓ Easing / Dormant / New* trend chip versus the previous comparable window. This is the &ldquo;what&apos;s actually moving off the counter&rdquo; counterpart to Production Stats&apos; &ldquo;what you&apos;re making&rdquo;.
- **Nested fillings (filling-in-filling)** — fillings can now contain *other fillings* as components, not just ingredients. The pattern shows up everywhere a chocolatier uses a base recipe inside a final filling: caramel base inside a caramel ganache, hazelnut praliné inside a gianduja layer, mendiant biscuit base inside a crunchy layer. Each filling's edit screen has a new **Nested fillings** section under the ingredients list with a search-and-pick form; the picker disables options that would close a loop (self-reference, A→B→A, etc.) and explains why ("Self", "Cycle", "Added"). Cost, allergens, and nutrition flow through the nesting tree automatically: the product cost breakdown sees every leaf ingredient through every level, allergens cascade up to every host filling when an ingredient changes, and the nutrition panel weights nested ingredients by the host's portion of the child recipe. - **Fillings-only production plans** — you can now produce filling batches on their own (no product required), and mix filling-only batches with product batches in the same plan ("hybrid plans").
- **Persistent storage request on app boot** — ChocCollab now calls `navigator.storage.persist()` on load so browsers that support it won't evict your IndexedDB under storage pressure. Settings → Backup shows a new **Device Storage** card with the current persisted state, usage/quota, and a manual "Request persistent storage" button for browsers (Safari, Firefox) that only grant the request on a user gesture.
- **Auto safety-snapshot before destructive operations** — both **Restore from backup** and **Delete all data** now download a timestamped JSON snapshot of your current data before wiping the database. A one-time green banner appears on the Settings page after the upgrade explaining what the file is and how to restore it.

Weigh the pan empty, cook the recipe, weigh the pan full, enter the difference once. The filling detail page then shows the raw-to-cooked reckoning under the ingredient total (e.g. `688g raw → 503g cooked · −185g (26.9%)`). When rescaling, ChocCollab uses the cooked yield as the base: asking for *600 g of caramel* in a production plan now produces 600 g on the scale after reducing, not 600 g of raw ingredients that cook down to ~440 g. Fillings without cook-loss (ganaches, pralinés) can leave the field blank and keep using the raw ingredient total as before — behaviour is unchanged until you enter a yield.
- **CSV ingredient import — sync options** — the CSV import on Settings → Import now exposes two opt-in checkboxes under a new "Sync options" panel in the preview step. *Update existing ingredients* turns the import into an upsert: rows whose name + manufacturer match an existing record now overwrite that record instead of being silently skipped as duplicates. *Remove ingredients not in this file* (only selectable alongside *Update*) deletes records whose keys are absent from the CSV — but only if they aren't referenced by any filling, product shell, or coating mapping; referenced ones are automatically kept and reported separately. The removal path requires an explicit two-step inline confirmation and downloads a safety snapshot first, matching the pattern used for *Delete all data* and *Restore from backup*. ### Fixed
- **"New production plan" page got stuck on "Loading…" on Cloudflare Pages** — only the Cloudflare-deployed build was affected; localhost dev was fine. The `_redirects` SPA-rewrite rule `/production/:id` was matching the literal string `"new"` as an id and serving the dynamic-route SPA shell for `/production/new`, so the browser loaded HTML meant for `/production/[id]` but under the URL of the new-plan wizard. React hydrated the wrong HTML and threw minified error #418. Added explicit `/production/new` pass-through rules that match before the catch-all, so Cloudflare now serves the correct static HTML for the static page. The hydration smoke suite (`npm run test:e2e:prod`) now includes a route-tree assertion that catches this class of bug locally.
- **Cost per gram was shown as 0 for ingredients priced in grams** — e.g. *2500 g at €80* displayed as `€0.000/g` instead of `€0.032/g`. The form used to silently default `g per unit` to 1000 regardless of whether the purchase unit was `g` or `kg`, inflating the total mass 1000×. The form now uses the definitional value (`g` → 1, `kg` → 1000) and the cost-per-gram calculation derives it directly from the unit, so every list, report, and detail view of an already-saved ingredient is corrected without any re-entry. Only `g` and `kg` are auto-set; `ml`, `L`, and `pcs` still take the density/piece weight you entered.
- **CSV ingredient import flagged user-created categories as "Unknown"** — the validator only recognised the built-in seed list (Chocolate, Fats, Sugars, …) and warned on anything else, even though a category the user had created in the app was valid and saved correctly on import. The validator now consults the live `ingredientCategories` table in addition to the seed list, so only genuinely unknown names are flagged.
- Hydration warning on first page load caused by the pre-hydration `data-nav-collapsed` script writing an attribute to `<html>`.
- **Cost per gram could still be saved as `€0.0000/g` when the `g per unit` field was typed into for purchases in `g` or `kg`** — follow-on to the v0.2.0 fix. The field was auto-filled to the definitional value (1 or 1000) on load, but remained editable, so users reading "g per unit" as "grams per package" could type e.g. 2500 for a 2500 g bag and multiply the total mass by 2500× on save. The live preview and the saved record both showed `€0.0000/g`. Reopening the ingredient appeared to fix it (the field was re-coerced on load) but the underlying row was still wrong until the next save. The field is now read-only for `g`/`kg` with a locked visual style, and the cost-per-gram preview plus the saved row derive `g per unit` directly from the unit — so legacy records rendered via the detail view are corrected immediately, without re-entry, and the save path always writes a self-consistent row. `ml`, `L`, and `pcs` remain editable as before.
- **Saving an ingredient could add two identical rows to its price history** — reproducing the bug above tended to produce a pair of price-history rows, one per save, with the same displayed `€X for Yg` line. Two independent causes: a rapid double-submit (click racing Enter) could slip past the async `saving` button-disable before React re-rendered, and the scenario above legitimately marked "price changed" on the repair-on-reopen save. The form now uses a synchronous reentrancy guard to reject overlapping submits, and `saveIngredientPriceEntry` skips the insert if the newest existing entry already has identical pricing fields.
- **Shell designs (and other seeded default lists) could appear twice after a backup restore** — every app load runs a `ensureDefault…` pass that tops up the shell-designs, filling-categories, ingredient-categories, decoration-categories, and product-categories tables from their seed list if any entries are missing. The check-then-insert wasn't atomic, so two concurrent runs (React StrictMode's double-mount in dev, SeedLoader racing `importBackup`'s post-restore reconciliation, or a Dexie Cloud sync retry) could both observe an empty table and each independently insert the defaults, producing duplicate "Airbrushing", "Brushing", etc. rows. The check + insert now runs inside a Dexie transaction, so concurrent callers serialise and the second one sees the first's writes. Prevents new duplicates; doesn't retroactively clean up existing ones — for that, delete the extras from the list page (or ask for a one-shot cleanup utility).
- **Shell-design dropdown on the product edit page snapped back to the first option ("Airbrushing") on every change** — the `onChange` handler called two separate state updates (`updateTechnique` then `updateApplyAt`) that each read the same stale `steps` from the closure, so the second call overwrote the first and reverted the technique change. The handler now applies both fields in a single update.
